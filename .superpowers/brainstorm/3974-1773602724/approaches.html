Agent Runner: Architecture Approaches

How should we relate this to terminar? Pick the approach that feels right.

A

Build inside terminar monorepo

New agent/ crate + web views. Reuse server, protocol, and web frontend directly. Ship as terminar-agent binary.

Architecture

Web Frontend (extended) ──WebSocket──► terminar-agent (new binary) │ xterm.js terminals │ │ agent dashboard views ├── PTY sessions (from server) │ conversation viewer ├── Agent orchestrator ├── Claude Code API bridge └── Agent registry

Pros

  • Maximum code reuse — PTY, history, protocol, web components
  • Fastest to prototype
  • Shared tooling (CI, tests, releases)

Cons

  • Terminar repo gets heavier
  • Release coupling between terminal tool and agent tool
B

New repo, import terminar as library

Separate project that depends on terminar-server as a Rust library crate for PTY management. Own protocol, own frontend.

Architecture

Agent Web UI ──WebSocket──► agent-server │ agent-specific views │ │ xterm.js (copy/fork) ├── uses terminar-server as lib ├── Agent orchestrator ├── Claude Code bridge └── Agent registry

Pros

  • Clean separation — terminar stays a terminal tool
  • Independent release cycles
  • Can evolve protocol for agent-specific needs

Cons

  • More upfront setup
  • Need to extract terminar-server into a reusable library crate
  • Web frontend partially duplicated
C

Agent layer on top of terminar (recommended)

New repo. Agent orchestrator connects to terminar-server as a client (via existing protocol). Adds agent-aware UI and Claude Code API integration on top.

Architecture

Agent Dashboard ──► agent-orchestrator ──► terminar-server (unchanged) │ agent status/logs │ │ │ conversation view ├── Claude Code bridge ├── PTY sessions │ embedded terminals ├── Agent registry ├── History buffer └── uses shell-protocol └── Persistence as client library

Pros

  • Terminar completely untouched — no risk to existing tool
  • Reuses shell-protocol package directly
  • Agent features cleanly isolated
  • Can run terminar-server as a dependency or embed it

Cons

  • Protocol may need extensions for agent use cases
  • Two processes to manage (agent-orchestrator + terminar-server)
